Important findings from first Android self-test
-----------------------------------------------
1. Mobile local cache/offline behavior must be tested on a real physical phone, not judged only from the emulator. The purpose is to verify that operational data is really cached locally on the device and survives app close/reopen, temporary network loss, and later synchronization.
2. Attendance/UI responsiveness needs work. Some items appear selectable but do not open/respond consistently when tapped. Screen transitions and touch behavior must be tested as real user flows, not only by checking that screens compile.
3. App performance currently feels laggy in emulator. Separate emulator/debug-build slowness from genuine app/API slowness before optimizing.
4. Bootstrap company admin is an administrator but does not automatically have every project operational permission. For development/demo self-testing, provide a deliberate full-access test/admin path without weakening production least-privilege authorization.
5. Identity must not create duplicate employees just because a person signs in differently. One employee/person record must be able to link multiple approved login identities, such as Google/Gmail, mobile number/OTP, company email, and future providers. All linked identities must open the same employee profile, memberships, permissions, project access, attendance history, DPR history, etc.

Required platform/operations work
---------------------------------
1. Replace manual PowerShell-based runtime startup for installed customer deployments with managed services.
   - API service.
   - Worker/background service(s) where required.
   - Web service/static hosting as appropriate.
   - Automatic start after machine reboot.
   - Health checks and controlled restart.
   - PowerShell scripts can remain as development/setup helpers, but normal customer operation should not depend on manually opening terminals.

2. Custom endpoint/domain support.
   - Customer-configurable API/web hostname/domain.
   - HTTPS/TLS in production.
   - Avoid hard-coded localhost or emulator addresses outside development.
   - Installation/configuration flow should validate the configured endpoint.

3. Setup, installation, and upgrade recovery.
   - If setup/install/upgrade fails, show the failed step and allow Retry/Restart instead of forcing the administrator to repeat everything manually.
   - Operations/admin UI should expose safe service restart where appropriate.
   - Setup should be resumable/idempotent where practical.
   - Include reset options for development/test/demo environments.
   - Production destructive reset must be protected, explicit, audited, and separate from normal recovery.

4. Backup before every rollout/upgrade.
   - Take PostgreSQL database backup before schema/application rollout.
   - Record backup file, timestamp, application version, database migration version, result, and operator.
   - Do not continue a risky migration if required backup fails.
   - Define rollback/recovery procedure.

5. Database export/import features.
   - Admin-controlled database export/backup feature.
   - Admin-controlled restore/import feature with validation and confirmation.
   - Import should not blindly overwrite incompatible schema versions.
   - Maintain audit trail for export/import/restore operations.
   - Prefer standard PostgreSQL backup/restore internally rather than inventing a custom database format.

6. Legacy data migration/import utility.
   - After a new customer installation is ready, provide a migration/import executable or guided tool to ingest legacy customer data.
   - Support mapping/validation before final import.
   - Produce import summary, rejected rows/errors, and reconciliation counts.
   - Keep this separate from full database restore: legacy migration is business-data ingestion; database restore is disaster recovery/backup restoration.

7. Logging is required.
   Maintain separate categories instead of one giant log file:
   - Application/API logs.
   - Background worker/job logs.
   - Installation/setup/upgrade logs.
   - Database migration logs.
   - Backup/restore/import/export logs.
   - Integration/synchronization logs.
   - Security/audit events for privileged user actions.
   - Mobile synchronization diagnostics appropriate for support, without logging secrets/tokens or unnecessary personal data.
   Logs should have timestamps, level, component, correlation/request/job identifier where useful, and safe retention/rotation.

8. Operations controls.
   - Service status/health.
   - Restart failed services/jobs.
   - Retry failed jobs where safe.
   - Database/backup status.
   - Storage status.
   - Integration/sync status.
   - Clear errors that explain the next action rather than generic failure messages.

Mobile/offline acceptance requirements
--------------------------------------
- Operational field data required for the current user's authorized projects should cache locally on the phone according to offline policy.
- Previously loaded permitted data should remain usable during temporary loss of network where offline operation is supported.
- Offline edits must queue locally and synchronize after reconnection.
- Sync must be idempotent: no duplicate attendance, DPR, upload, or work-progress records after retry/reconnect.
- Force-closing and reopening the app must not lose committed local work.
- Authentication/security/financial authority that is intentionally online-only must remain online-only.
- Provide understandable pending/synced/failed state to the user.

Identity/account requirement
----------------------------
- Separate Person/Employee/Worker from Login Identity.
- One person may link multiple verified authentication identities.
- Example identities: Google account, mobile number/OTP, company email, future SSO.
- Do not create a second worker/employee automatically when the same person uses another sign-in provider.
- Linking/unlinking identities must be controlled and audited.
- Permissions and memberships belong to the Construction OS person/membership context, not independently to each external login identity.

Development/testing rule
------------------------
A module is not considered usable merely because API tests and Android/web builds pass. For user-facing workflows, test the complete task from the user's perspective and record friction such as dead taps, lag, excessive steps, unclear messages, lost state, poor offline behavior, or difficult recovery.

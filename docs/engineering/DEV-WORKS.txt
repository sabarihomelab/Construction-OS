1. PRODUCT IDENTITY AND GOAL
============================
Construction OS is an India-first construction operating platform for small and mid-sized civil/general contractors, builders, MEP contractors and specialty subcontractors.

Core product principle:

    Complex underneath. Simple on top.

Construction OS should connect the contractor's project operating workflow rather than behave like many disconnected mini-apps.

The integrated business direction is:

    Company
      -> Project
      -> Party / Business Partner
      -> WBS / Cost Codes
      -> BOQ
      -> Estimate / Rate Analysis
      -> Budget
      -> Workforce / Crews / Attendance
      -> DPR / Work Quantity / Progress
      -> Material Requirement / Indent
      -> Approval
      -> RFQ
      -> Vendor Quotes
      -> Comparison
      -> Purchase Order
      -> Delivery / Challan / GRN
      -> Site / Store Inventory
      -> Material Issue / Consumption
      -> Equipment Usage
      -> Measurement / Certification
      -> Subcontract / Work Order
      -> Subcontractor RA Bill
      -> Client Measurement / RA Bill
      -> Job Cost / Planned vs Actual
      -> Dashboard / Reports
      -> Excel / Accounting / Tally bridge
      -> Closeout basics

The final Release 1 test is not "how many modules exist?".
The final test is:

    Can one real Indian contractor run one real project through Construction OS
    from BOQ and site execution through procurement, measurement, RA billing,
    cost control and management visibility without manual database edits,
    fake UI-only data, dead controls or broken workflow stages?

4. IMPORTANT DOMAIN RULES THAT MUST NOT BE LOST
===============================================
4.1 Party model
One reusable Party / Business Partner foundation must represent roles such as client, vendor, supplier, subcontractor, consultant and service provider. Do not create unrelated duplicate masters for the same organization.

4.2 WBS vs BOQ
WBS / Cost Codes are the internal project control and cost structure.
BOQ is the contractual quantity/rate/billing structure.
They are related but are NOT the same object.

4.3 Worker is not User
A labourer/worker can exist without owning an application login.
Supervisor-driven bulk attendance is a core workflow.

4.4 Employee / Person is not Login Identity
One real employee/person can have multiple verified login identities linked to the same Construction OS person/profile.
Examples:
- Google / Gmail account.
- Mobile number / OTP.
- Company email.
- Future SSO identity.

Using a second login provider must NOT create a second employee automatically.
All linked identities must resolve to the same person, memberships, permissions, project access, attendance/DPR history and business context.
Linking/unlinking identities must be controlled and audited.

4.5 Quantities and money
Authoritative quantities and money use Decimal/Numeric semantics.
Do not store authoritative values only as descriptive text.
Incompatible units must never be silently converted.

4.6 Inventory
Stock is derived from traceable transactions, not manually edited balances.
Examples include opening balance, GRN receipt, issue, consumption, transfer, return, rejection, wastage, damage and controlled adjustment.

4.7 Measurement
Measurement/certification is a reusable business engine.
Preserve separate states such as executed, measured, submitted, certified, billed and paid quantities.

4.8 RA billing
RA billing is cumulative.
Previous/current/cumulative quantities and amounts must remain reproducible.
Deductions/additions such as retention, advance recovery, material recovery, penalties, withholding and tax must be configurable/effective-dated rather than hardcoded forever.

4.9 India commercial/compliance
GST/TDS/withholding/e-invoice architecture must be jurisdiction-aware, versioned and effective-dated.
Historical approved/certified/posted records retain the exact applied rule version.

4.10 Accounting
Construction OS owns operational and construction-commercial truth.
Accounting remains adapter-driven.
Initial adoption priority is controlled Excel/CSV, then Tally integration.

11. FIRST ANDROID SELF-TEST FINDINGS - OPEN
===========================================
These findings are product defects/usability requirements, not just emulator notes.

11.1 App feels laggy
The Android debug/emulator experience currently feels laggy.
Possible contributing factors include emulator image, debug build and host load, but genuine app/API/UI inefficiency must not be dismissed.

Required later:
- Profile actual screen/navigation/network/database behavior.
- Distinguish UI rendering lag from API latency and local database work.
- Test release-like build on a physical phone.
- Avoid accepting field screens that visibly lag.

11.2 Touch / responsiveness problems
Some UI items appear tappable but do not consistently open/respond.
Attendance was specifically observed as a flow where taps/actions did not always behave as expected.

Requirement:
A module is not "done" because its screen renders. All important buttons/cards/rows must respond immediately and clearly.

11.3 Admin cannot automatically perform every project operation
The bootstrap company administrator currently does not automatically get every project-scoped operational permission.
Attendance and DPR use independent action permissions such as create/update/submit/approve.

Production principle:
Keep least-privilege authorization.

Development/demo requirement:
Provide a deliberate full-access development/test admin path so the bootstrap tester can exercise every demo workflow without manually assembling many roles.
Do NOT weaken production security to solve a development inconvenience.

11.4 Real local caching must be proven on an actual phone
The requirement is not merely "the emulator runs offline".
Operational field data must truly cache locally on the physical Android device, survive app close/reopen and sync correctly after connectivity returns.

11.5 Real-device usability is mandatory
A final mobile UX judgement cannot be made only from emulator screenshots.
Real-phone testing must cover:
- touch responsiveness,
- scroll behavior,
- keyboard behavior,
- camera/gallery,
- app background/foreground,
- force-close/reopen,
- low/poor connectivity,
- offline work,
- sync recovery,
- interrupted uploads,
- battery/data behavior,
- outdoor readability,
- one-handed/site usage where realistic.


12. MOBILE / OFFLINE ACCEPTANCE REQUIREMENTS
============================================
Offline/low-bandwidth is a Release 1 baseline for field-critical workflows.

Operational data in scope includes, where safe/authorized:
- Attendance.
- DPR.
- Work progress / quantities.
- Photos/media metadata and durable upload state.
- Material transactions.
- Equipment usage.
- Issues.
- Inspections.
- Safe measurement capture.

Required behavior:
- Local save must be immediate and visible.
- Previously loaded permitted data remains usable during temporary network loss where offline operation is allowed.
- Offline mutations are durably queued on the device.
- Retry uses backoff and idempotent identifiers.
- Reconnection must not create duplicate attendance/DPR/progress/upload records.
- Force-close/reopen must not lose committed local work.
- Pending/synced/failed states must be understandable to the user.
- Conflicts must surface explicitly rather than silently overwrite authoritative data.
- Authentication/security/financial authority intentionally designated online-only remains online-only.

Real phone validation must prove that the local cache is genuinely stored on the device and is not only a temporary emulator/server artifact.


13. IDENTITY / ACCOUNT REQUIREMENT - OPEN DESIGN/IMPLEMENTATION
===============================================================
Separate these concepts:

    Person / Employee / Worker

from:

    Authentication Identity / Login Provider

A person may have multiple verified identities.
Example:
    Employee Sabari
      -> Google identity A
      -> verified mobile number
      -> company email identity

All identities must resolve to the same Construction OS person context.

Required properties:
- No duplicate employee automatically created when a new provider is used.
- Controlled identity linking.
- Controlled unlinking.
- Strong verification before linking.
- Audit record for identity changes.
- Conflict handling if a provider identity is already linked elsewhere.
- Recovery path if a user loses one provider.
- Permissions belong to membership/role context, not separately to Gmail/mobile identities.
- Worker records may continue to exist without any app account.

This requirement must be included in the identity/auth architecture before production rollout.


14. INSTALLATION / RUNTIME / SERVICE REQUIREMENTS - PENDING
===========================================================
Current development startup uses PowerShell scripts such as start-local.ps1.
This is fine for development but NOT the desired normal customer runtime operation.

14.1 Managed services
Installed customer deployments must run as managed services/processes rather than requiring the user to manually keep PowerShell terminals open.

Required managed runtime components as applicable:
- API service.
- Background worker/job service(s).
- Web/static hosting service.
- Supporting scheduler/worker processes as the platform grows.

Required behavior:
- Start automatically after machine/server reboot.
- Stop/start/restart cleanly.
- Expose health/readiness.
- Restart safely after recoverable failure.
- Record service status and relevant failures.
- Upgrade process can stop, migrate and restart services in a controlled sequence.

Do not lock into a Windows service implementation technology until the deployment design is reviewed, but normal operation must not depend on manually launching PowerShell.

14.2 Custom endpoint/domain
Each customer installation must support configurable endpoints/domain names.
Requirements:
- Customer-configurable web hostname/domain.
- Customer-configurable API hostname/domain if separately exposed.
- Production HTTPS/TLS.
- Certificate configuration/renewal plan.
- Environment-aware CORS / trusted origins.
- Mobile connection must use the configured deployment endpoint.
- No production hardcoding of localhost, 10.0.2.2 or 127.0.0.1.
- Installer validates endpoint reachability/health before completing setup where practical.

14.3 Setup/install/upgrade recovery
Setup must not become "rerun random commands until it works".

Requirements:
- Clear step-by-step installer stages.
- Persist setup progress/state.
- If a step fails, show the exact failed step.
- Provide Retry for safe retryable steps.
- Provide Restart/Resume for the installer workflow.
- Make setup idempotent where practical.
- Validate dependencies before destructive work.
- Do not silently ignore partial failures.
- Produce supportable setup logs.

14.4 Reset / recovery options
Need reset/recovery features with clear environment boundaries.

Development/test/demo:
- Reset demo data.
- Reset test company/workspace where explicitly requested.
- Recreate seed data.
- Restart local services.

Production:
- No casual destructive reset.
- Explicit confirmation.
- Strong authorization.
- Audit event.
- Backup requirement before destructive action.
- Clear scope: cache reset vs service restart vs data reset must not be confused.

14.5 In-app/admin recovery controls
Operations/admin UI should eventually support safe controls such as:
- View service health.
- Restart safe application service/process where permitted.
- Retry failed background job.
- Refresh integration.
- View backup status.
- View storage status.
- View database readiness.
- See actionable failure message and recommended next step.

16. DATABASE BACKUP / EXPORT / IMPORT / ROLLBACK - PENDING/HARDENING
==================================================================
16.1 Backup before every rollout/upgrade
Before a risky application/schema rollout:
- verify database connectivity,
- take a PostgreSQL backup/snapshot,
- verify backup completion,
- record timestamp,
- record app version/commit/release,
- record DB migration version,
- record operator/system action,
- retain backup according to policy.

If the required backup fails, the migration/upgrade must not continue as if everything is safe.

16.2 Rollback/recovery
Define deterministic recovery:
- application rollback strategy,
- schema migration compatibility rules,
- database restore procedure,
- file/storage compatibility considerations,
- service restart order,
- health validation after recovery.

Do not promise automatic rollback if the underlying schema migration is irreversible. Irreversible changes must be explicitly designed/flagged.

16.3 Database export feature
Admin-controlled export/backup is required.
Possible outputs should use standard PostgreSQL backup mechanisms internally rather than inventing an opaque proprietary database format.

Required:
- authorization,
- progress/result,
- checksum/integrity information where useful,
- audit trail,
- secure storage/download handling,
- version metadata.

16.4 Database import/restore feature
Admin-controlled restore/import is required.
Requirements:
- validate backup format/version,
- show target deployment/database,
- explicit confirmation,
- compatibility check,
- protect against blindly restoring incompatible schema,
- audit the action,
- verify post-restore health.

16.5 Database restore vs legacy import are different
Database restore:
    Disaster recovery / full environment data restoration.

Legacy import:
    Mapping a customer's previous Excel/database/software data into Construction OS business records.

These must remain separate tools/workflows.

20. AUTHORIZATION / ROLES REQUIREMENTS
======================================
Backend/server remains authoritative for permissions.
Never rely only on hidden buttons in the UI.

Authorization can differ by:
- organization/company,
- project,
- resource,
- action,
- role/membership,
- workflow state.

Examples of independent Attendance actions already represented in the permission model include concepts such as:
- view,
- create,
- update,
- submit,
- approve.

DPR similarly separates create/update/submit/approve/manage behavior.

Production:
- Maintain least privilege.
- Admin/security role does not automatically imply every business action unless product policy explicitly says so.

Development/demo:
- Add an intentional full-access testing capability so a developer/admin can test the integrated demo end to end.
- This must be clearly development/demo scoped or implemented as a deliberate all-business-permissions test role.
- Never achieve this by bypassing authorization checks globally.

25. QUALITY / DEFINITION OF DONE
================================
A route/model/screen/button existing is NOT enough.

A capability is complete only when applicable requirements are satisfied across:

Functional
- End-to-end real user workflow works.
- Canonical data is persisted.
- Validation/business rules are server-enforced.
- Loading/empty/success/error/conflict states are handled.

Security/privacy
- Authentication/authorization enforced.
- Tenant/project isolation tested.
- Sensitive values kept out of logs.
- Audit where appropriate.

Reliability
- Transaction boundaries are correct.
- Critical retries are idempotent.
- Long-running effects use durable jobs/outbox where appropriate.
- Failure modes are observable.

Quality
- Domain unit tests.
- API/integration tests.
- CI lint/type/build.
- Migrations included and safe.
- Contracts/documentation updated.

UX
- Target-device usability verified.
- Field actions minimize typing.
- Destructive actions protected.
- No fake/placeholder controls shipped as complete.
- No dead taps.
- No unexplained generic errors where an actionable message is possible.

Operations
- Required configuration documented.
- Health/readiness defined.
- Backup/restore impact understood.
- Important failures observable.

Documentation/support
- Admin/user behavior documented.
- Troubleshooting guidance exists.

28. INSTALLATION / UPGRADE TARGET EXPERIENCE
============================================
Long-term customer experience should look approximately like this:

NEW INSTALLATION
1. Run installer/setup.
2. Validate machine prerequisites.
3. Choose/configure deployment profile.
4. Configure database.
5. Configure endpoint/domain and HTTPS.
6. Configure file storage.
7. Install/initialize services.
8. Apply migrations.
9. Bootstrap company/admin.
10. Configure enabled modules.
11. Start services.
12. Run health/readiness validation.
13. Optionally launch legacy import/migration tool.
14. Complete setup and show admin URL/status.

UPGRADE
1. Read current installation state/version.
2. Validate prerequisites/free space/DB connectivity.
3. Create and verify database backup.
4. Stop controlled services as required.
5. Apply application update.
6. Apply safe migrations.
7. Start services.
8. Health/readiness validation.
9. Run post-upgrade checks.
10. Record result/version/backup details.
11. Provide rollback guidance if validation fails.

FAILED INSTALL/UPGRADE
- Show failed stage.
- Preserve prior completed stages.
- Offer Retry/Resume/Restart where safe.
- Preserve logs.
- Do not leave the user guessing which PowerShell command to run next.
